# NeuroSurge: keep the held input

Package edition: experimental-2026-11-11-capture-update.

A visible hand makes the effect of a control concrete. A colour link gives you something to follow from a brain area to a muscle group and back. That is the job of this game. Its atlas surfaces describe human anatomy; its activity values and movements are generated by rules. A convincing movement does not establish that the corresponding brain location would produce it in a person.

## A repeated notification is not a fresh capture

A pointer-capture notification used to clear keys before the controller checked whether capture had changed. A repeated captured notification could therefore release a held fist and discard a pointer gesture while play stayed active. The controller now reads the actual captured state first. When both that observation and its cached state are captured, it clears the old pending-request/fallback flags and keeps the keys, records and current gesture. It adds no click or lock-change callback.

A genuine acquisition or loss still takes the existing release path. An uncaptured notification remains conservative, including duplicates. Esc, modifier shortcuts, blur and visibility behavior are unchanged. The guard uses the state actually observed; it does not reconstruct an unobserved past transition or identify the cause of a previous input failure.

In the preceding candidate, eight ordinary local browser states covered Space/W/D, modifier safety release, a fresh press/release and Esc pause/resume. They did not establish that the new duplicate branch was reached. Earlier failed Space/W/D cases remain failed with cause unknown.

The first candidate read capture before a synchronous safety callback. Review found that an optional callback could change that state. The final code keeps the original post-callback read on genuine boundaries. Two new supplied-data cases failed on that first candidate and passed on the corrected code; the original 62 capture cases and 64 regression cases also passed, giving 128 current named cases. A final source-header clarification changes comments only, with an exact mapping back to the tested code.

## Esc should answer the next press

The browser uses Esc to release pointer capture. That release already pauses the game, and a delayed keydown from the same press must not immediately close the instructions again. A time-only guard also swallowed a genuine second press.

The game now records an observed Esc release separately from pointer-lock changes. A subsequent press can resume promptly after that release. Repeated held-key events are ignored. Without release evidence, the existing 400 ms guard remains the fallback; the game does not invent a keyup. Focus, visibility and lifecycle changes discard the key-release record. Resuming by Esc does not request pointer capture, so a click is still needed to capture it again.

In the local check of the merged control build, pause and rapid resume both worked. The resumed-state readback came within about 212.9 ms of the observed unlock, with a commanded 50 ms key gap. This does not measure input-to-GPU display latency or pass the 100 ms requirement. Naturally missed releases and comprehensive browser event-order coverage remain unverified.

## A movement limit should explain itself

The whole-arm route checks whether the requested view can show the arm and hand. Recovery tries smaller requests or a previous view rather than accepting an unchecked pose. The camera's retry work also rolls back an unshown E transition on this route. The ordinary check completed first-to-third-to-first changes, but it did not reach the natural failure and recovery boundaries. The same rollback has not been established for other camera routes.

The frame loop still has an incomplete late boundary. A failure after model state, scene state or rendering has advanced can leave them out of step. The bounded input repair below does not make that transaction atomic or authorize replay of already committed events.

## A waiting release needs a place in the queue

Keeping the first 64 records could lose a later Space-up. Rescue could then invent a new, unstamped safety-up from whatever survived. The application now checks the combined carried and fresh record count before draining either queue, assigning frame offsets, changing camera view or binding a plan. Within the same 64-record bound it retains the entire raw list, preserving supplied fields, timestamps and order through repeated refusals. Applying the existing carry bound to the combined list is an engineering saturation policy, not a measured optimum or a user-selected physiological limit.

Above that bound the game cancels the waiting input as a distinct policy. It releases held controls, clears stale E/drag/orbit requests and transient carry anchors, and queues one safety-up at its actual observation time. The player sees a release-and-press-again notice. Normal releases keep their old behavior; an App-owned pre-safety callback checks capacity before the adapter reads state, so cancellation is not overwritten by an old reducer snapshot. Queue-cleared copies avoid visiting old history during that cancellation. Pending-record counts include generated safety releases and are not counts of physical actions.

The unchanged long-skip rescue now uses that same explicit boundary instead of an unstamped coalesced release. Ordinary below-bound retries retain the existing pre-E snapshot/redo scheme. An overfull defensive refusal branch does not requeue canceled E or drag. None of this repairs the later model/scene/render commit boundary. The click reducer's earlier drop-new limit is also separate.

For the earlier input-queue edition, five syntax checks and three software suites passed: 11 new cases, 13 cancellation cases and 40 pointer cases. Supplied in-memory records and adapter doubles establish those state properties; a declared-count proxy avoids allocating huge histories. They establish no physical input rate, displayed latency or native overflow/recovery result. Three subsequently corrected comment lines left executable and test bytes unchanged.

Earlier ordinary browser checks exposed an unresolved fast Space/W/D loss in the input-queue candidate and the preceding pause-update build. Later sequences worked. Source review lists possible key-up and safety-release routes, including modifiers and pointer-lock notifications, but existing snapshots do not identify which one occurred. Do not turn that list into a claimed cause or regard a running frame as complete input acceptance.

## A pause should leave old input behind

Waiting for a paused animation frame was too late. A quick resume could reuse clicks, turns or an E request from before the pause. The application now clears fresh and deferred input synchronously on both sides of the play boundary. It also ends the binding's private mouse gesture, keeps the current press number and starts the arrow consumer from that number. The next genuine press therefore has a new identity; an unseen old press cannot become a new arrow command.

Cancellation drops those queued actions deliberately. One marked safety release takes their place at the observed cancellation time, so the normal activity step can open a held fist and end a tap chain. A temporary brain grab, view grab and camera anchors are cleared without changing saved placement, pose or elapsed simulation time. Otherwise a new gaze could move the brain before the queued release was reached. Resets and focus/lifecycle boundaries use the same mechanism. Observed graphics loss/restoration cancels input without changing the existing wall-clock pulse aging; that branch remains source-reviewed rather than natively exercised.

The new pure software suite passed 13 named cases and 128 keyboard-state combinations. A separate ordinary Chromium check recorded 15 states: brain carry and pause/resume, an interrupted arrow hold and fresh click, both E directions and the visible Reset body command. The brain's saved position stayed exact across that one pause/resume case. These observations do not establish a pause with no intervening animation callback, all focus/lifecycle paths, pixels or the original input-to-display timing. Overflow/rescue native qualification and late state/render failures remain separate open work.

## Let the next press start a new gesture

A browser can miss the event that says a mouse button was released. The old controller could end an object drag while leaving its button state held, or keep an arrow hold armed. The next press then inherited the old gesture instead of starting its own.

The controller now handles a reliable all-buttons-up observation before the arrow and drag branches return. It clears the pending pointer gesture, ends the drag without emitting a click and marks the button up at the time of that observation. It keeps the press sequence so a new down increments it once. This cancellation leaves keyboard keys alone. Esc, blur and visibility changes clear the pointer flags as well as invoking their existing safety release.

For the prior pointer-release controller, independent Node testing passed 40 named cases; the same cases produced 20 assertion failures with the previous controller. The cases include all 32 key states across four pointer modes, arrow release, a fresh tap after cancellation, partial multi-button releases and focus/Esc callbacks. They exercise in-memory event records through the public controls API. They do not establish native pointer-lock behavior, a physical release time, visible latency or complete input recovery. The game uses the first reliable observation; it does not reconstruct the event that went missing.

## Turn an object; carry it somewhere else

Dragging turns the brain or mirror around its centre. Holding Space carries the selected object with the look and simultaneous W/A/S/D movement, within finite travel limits. The two gestures have separate jobs, and carrying takes precedence. The brain can block mirror carrying and turning until it is moved aside.

Muscle clicks use a different rule: they may pass through clear brain glass to select a visible muscle. Motor areas take priority. This relaxes the earlier all-glass click blocker for muscle selection while retaining the blocker for mirror carry and orbit. The selected response belongs to a representative movement group. It is not a precise one-muscle cortical address.

## Give the arrows a stable place

The ribbon arrows curve away into the scene and offer click/hold turns without an idle spin. Their nominal placement uses the brain's reference framing, rather than following each new outline as the brain rotates. A resize can refresh that reference. This is intended to keep the controls findable while the object turns.

In the earlier control-build check, two ordinary right-arrow clicks turned the brain. The recorded brain centre and all four nominal CPU arrow anchors stayed exactly unchanged across those samples. That supports this one case. It does not establish identical pixels, GPU buffers, every arrow, every view or safe clearance from every motor area. The top arrow remains close to the edge, the player's arm can hide an arrow, and the two objects' arrows can overlap.

## Keep the anatomy and its display choices distinct

The brain's framing was changed to show more of its outline around the motor band. Its anatomy and motor labels share the same transform; nothing here establishes validated functional registration. The projection can stretch the brain at steep viewing angles. Some lower lateral regions need the brain turned before they can be aimed at; no claim that every region is reachable from the default view is made.

The ordinary body view hides surfaces behind the face-facing plane, because the camera backs away to fit the whole left arm. That is a display compromise, not a literal eye-level camera. Looking down shows the lap and legs without a complete first-person chest and belly. The mirror and the posterior view provide other ways to inspect the body. The separate floating face remains off.

Surface shading shares directions across coincident atlas vertices. It does not fill anatomical openings or establish smooth, accurate anatomy. The current pictures still contain splotchy and jagged muscles. Lifted outer muscles expose deeper layers as a display option; they are not physically separated that way in a living body.

The palm turn combines forearm pronation/supination with a small rotation at each hip. Those joints have separate axes, but their coupling is a game choice, not a universal anatomical law. The right upper-arm turn and matching hip-muscle colour remain incomplete. The left shoulder blade and collarbone slide with the arm; their motion has not been validated against a real reference series. Shared own-body/mirror poses do not settle those mechanics.

## Reuse calculation without claiming a frame-rate result

The code caches repeated visibility questions and uses a triangle search tree for rigid-mesh picks. Nonfinite inputs and parallel ray/box boundaries have explicit handling. Source review supports bounded implementation properties; it does not establish complete mathematical equivalence or a hardware speedup. The current screenshots include a slow-render notice, and independent hardware frame-rate measurements remain absent. Earlier author benchmark tables are not reproduced as release evidence.

## Fit the window before claiming a platform

Portrait layout remains unfinished. A previous composition failed to fit at 375 × 667 and was crowded at 390 × 844. Those observations are historical warnings, not results for this exact package. The current check supplies no new portrait acceptance. A wider desktop window is the practical starting point; touch, phones and tablets remain unverified.

Windows and macOS launcher formats have been checked as files, not run on those operating systems. An earlier Linux installer and desktop launch worked; execution with this package's updated online target still needs verification. Browser rendering, accessibility, reduced motion, full-arm borders and the upper-quarter hand position need broader checks. The one-second pulse target (±0.05 s), readable two-second startup interval and 100 ms input-to-frame requirement have not been fully accepted. Normal joint mechanics, held-out functional mapping and complete exports also remain unfinished.

## What the checks establish

In the earlier control build, seven sampled ordinary states remained running with no reported error: initial play, Esc pause/resume, Space held/released and E in both directions. CPU readbacks described current calculated state; they do not prove which exact frame a graphics device displayed. The two arrow clicks add one bounded orbit observation. The earlier browser observations remain historical. The current four software suites passed 128 named cases with the corrected controller and helpers; they establish the bounded software state transitions described above. No complete control tour, natural overflow/recovery test, physiological validation or finished-game acceptance follows.

Human anatomical structure is a constraint on a future functional model. To claim a trained decoder, a separate model such as NeuroTranslate 0.0 would need qualified neural and bodily recordings, declared units and clocks, independent movement measurements and held-out tests. This preview supplies a game to explore, with the gaps above left visible.
